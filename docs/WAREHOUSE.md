# Общий склад CRM → аналитика

Раздел «Общий склад» (`?page=warehouse`) получает снимок физического склада через серверный HTTPS-запрос. Редактирование учёта и резервирование остаются в CRM. Раздел обновляется каждую минуту, пока открыт; сервер переиспользует снимок не более 30 секунд. Фонового копирования остатков в базу нет.

Настройки приложения: `WAREHOUSE_CRM_URL` и `WAREHOUSE_EXPORT_KEY`. В CRM задаётся тот же новый ключ в `WAREHOUSE_EXPORT_KEY` (минимум 32 символа). Это отдельный ключ только чтения одного маршрута `/api/integrations/warehouse-export`, без доступа к финансам, сотрудникам и изменениям. Не публиковать ключ. Отсутствующий/неверный ключ закрывает выгрузку.

Доступ на стороне аналитики: реальный пользователь `FIRST_ADMIN_EMAIL` с одной полной membership owner без shop_ids; суперадмин/поддержка и MCP не обходят проверку. Общий физический склад не раскрывается ограниченным пользователям. Связи магазинов хранятся в warehouse_links, отдельно от API-ключей и исходных остатков.

Автосвязь: совпадение идентификатора владельца кабинета WB (oid из уже сохранённого токена) или Client-Id Ozon, переданное хэшем только между серверами. При отсутствии oid WB проверяется совпадение всего токена по хэшу. Неоднозначные связи не выбираются автоматически. Ручная связь требует того же маркетплейса и магазина владельца. Товар сопоставляется только по точному SKU в product_aliases выбранного магазина CRM, без нечёткого поиска.

Прогноз: WB берёт avg_orders из существующего stock_plan, Ozon — (orders_qty − cancel_qty) / 28 из oz_svod за 28 полных дней. Остатки магазина берутся из аналитики; склад, закупки и активные перемещения — из CRM. Потребность = ceil(спрос × (целевой запас дней + доставка дней) − остаток магазина − активные FBO-перемещения), минимум 0. Если нет данных спроса/остатка, расчёт отсутствует. Устаревший кэш отчёта не используется для рекомендованной отгрузки.

Свободный собственный склад уже уменьшен резервами CRM. Не вычитать их второй раз. Закупки в пути, фулфилмент, активные резервы и отправленные партии показаны отдельно и не входят в доступный для распределения пул. Принятые FBO-поставки не прибавляются к остатку, который уже приходит от маркетплейса.

Рекомендации расходуют общий пул один раз, приоритет — минимальный запас дней, затем ID магазина. CSV — план, а не создание поставки и не резерв. Снимок для просмотра не меняет бухгалтерию, рекламу или карточки.

Проверки: Python unit tests, существующие тесты CRM, PostgreSQL migration/UPSERT/unique constraints на временной PGlite-базе, TypeScript/Vite. Промышленная приёмка: ключ без авторизации → 401, корректный ключ → снимок; вход владельца → сопоставление магазинов и реальные строки; сравнить один артикул с CRM и отчётом аналитики.
